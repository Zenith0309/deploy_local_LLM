# Agent 完整教程：从模型调用到工具驱动的任务执行

## 1. 为什么需要 Agent

普通大语言模型调用通常是：

```text
输入上下文 → 模型 → 文本输出
```

这种方式适合问答、改写、摘要和分类，但它不能可靠地读取实时数据库、检查文件、调用业务 API 或确认任务是否真的完成。

Agent 在模型之上增加目标、工具、状态和执行循环：

```text
任务目标
   ↓
模型判断下一步
   ↓
工具执行
   ↓
观察结果进入上下文
   ↓
模型继续判断或给出最终答案
```

Agent 的本质不是“模型突然拥有了能力”，而是一个由模型决策、工具执行和运行时约束组成的闭环系统。

## 2. Agent 的组成

| 组件      | 主要职责               | 不能单独承担的事情    |
| ------- | ------------------ | ------------ |
| 模型      | 理解上下文、生成答案、选择工具    | 不能可靠执行权限检查   |
| 系统指令    | 描述角色、目标、规则和输出格式    | 不能替代代码安全控制   |
| 工具      | 读取数据、调用 API、执行受控动作 | 不能自行决定是否授权   |
| 状态      | 保存任务进度和中间结果        | 不能代替一致性设计    |
| 执行器     | 循环调用模型和工具          | 不能跳过验证       |
| 验证器     | 检查格式、业务规则和完成条件     | 不能保证模型事实一定正确 |
| Harness | 管理生命周期、权限、预算、恢复和审计 | 不是模型本身       |

## 3. 从普通聊天升级为 Agent

### 阶段 1：结构化输出

先让模型按照固定 Schema 输出：

```json
{
  "intent": "search",
  "query": "本地模型部署",
  "confidence": 0.86
}
```

这一步可以验证模型是否能稳定表达意图，而不必立即执行副作用。

### 阶段 2：只读工具

例如提供：

- `list_documents(directory)`
- `search_documents(query)`
- `get_system_status()`

只读工具更容易回滚，也更适合调试工具参数和错误处理。

### 阶段 3：受控写工具

例如：

- `create_draft(title, content)`
- `update_ticket(ticket_id, fields)`
- `send_message(recipient, body)`

写操作需要权限、审批、幂等键、审计和失败恢复，不应直接沿用只读工具的实现方式。

## 4. 工具设计

### 4.1 工具应该表达业务动作

不推荐：

```text
execute_shell(command: string)
```

更推荐：

```text
search_logs(
    service: string,
    start_time: string,
    end_time: string,
    level: "error" | "warning" | "info"
)
```

工具越接近业务动作，参数越容易校验，权限越容易限制，输出也越稳定。

### 4.2 工具 Schema

工具定义至少应描述：

- 名称和用途。
- 必填参数和类型。
- 枚举值、长度、范围和格式。
- 哪些参数互斥或必须同时出现。
- 是否只读。
- 可能产生的副作用。
- 错误类型和返回结构。

示例：

```json
{
  "name": "read_document",
  "description": "读取允许目录中的一个 Markdown 文档",
  "parameters": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string",
        "description": "相对于知识库根目录的路径"
      }
    },
    "required": ["path"],
    "additionalProperties": false
  }
}
```

### 4.3 工具返回值

不要只返回一段模糊文本。建议包含：

```json
{
  "ok": true,
  "data": {
    "title": "..."
  },
  "error": null,
  "meta": {
    "source": "local-kb",
    "duration_ms": 24
  }
}
```

错误也应该是机器可读的：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "PATH_NOT_ALLOWED",
    "message": "路径不在允许的知识库目录中",
    "retryable": false
  }
}
```

## 5. Agent 执行循环

一个健壮的循环应该明确区分模型输出、工具调用和最终答案：

```text
初始化任务
while 任务未结束:
    检查取消、超时、步数和预算
    组装最小必要上下文
    调用模型
    解析结构化结果

    如果是 final:
        验证答案
        成功结束，或回到模型要求修正

    如果是 tool_call:
        校验工具名称
        校验参数 Schema
        检查权限和审批
        执行工具
        限制结果大小
        记录调用并追加 observation
        继续循环

    如果格式错误:
        有限次数地请求模型修正
        仍失败则安全结束
```

必须设置：

- 最大步骤数。
- 单次模型调用超时。
- 单次工具调用超时。
- 总任务超时。
- 最大输入和输出长度。
- 最大重试次数。
- 成本或资源预算。

没有停止条件的 Agent 不是“更自主”，而是不可控。

## 6. 上下文工程

模型上下文通常包括：

```text
系统指令
+ 用户目标
+ 对话历史
+ 工具定义
+ 工具调用结果
+ 检索到的外部内容
+ 当前任务状态
```

### 6.1 上下文不是越长越好

过长上下文会带来：

- 更高的内存和延迟。
- 更高的模型混淆概率。
- 更难定位错误来源。
- 更高的敏感信息泄露风险。

建议：

- 保留当前任务真正需要的历史。
- 对旧对话做摘要。
- 工具结果只保留必要字段。
- 大文档使用检索而不是全部塞入提示词。
- 为外部内容标注来源和不可信边界。

### 6.2 指令层级

可以把消息分为：

1. 系统约束：角色、边界和输出契约。
2. 开发者约束：业务规则和工具使用规范。
3. 用户目标：本次任务。
4. 工具结果：外部观察数据。

工具结果和网页内容不应被当成新的系统指令。即使文本中出现“忽略之前规则”，也只应作为数据处理。

## 7. 记忆设计

### 短期记忆

保存当前任务的消息、工具结果、检查点和错误。任务结束后可以删除或归档。

### 长期记忆

适合保存稳定、经过用户同意且有来源的信息，例如语言偏好或项目约定。每条记忆最好包含来源、创建时间、更新时间和删除机制。

### 外部知识

RAG 通过检索文档提供事实，不等于 Agent 记住了所有文档。检索结果应包含来源、片段和相关性信息，让最终回答可以引用证据。

## 8. 规划与反思

### 什么时候需要规划

规划适合：

- 任务有多个依赖步骤。
- 工具调用成本较高。
- 需要先检查环境再执行。
- 需要向用户展示执行计划。

简单问题不必强制生成长计划。规划本身会增加 token、延迟和错误面。

### 反思不是万能药

让模型“再检查一次”有时能发现格式问题，但不能保证事实正确。可靠验证应尽量使用：

- Schema 校验。
- 单元测试或固定评测。
- 数据库约束。
- 权限系统。
- 确定性计算。
- 人工审批。

## 9. 安全边界

### 9.1 提示词注入

用户、网页、PDF、代码和数据库内容都可能包含恶意指令。防护重点：

- 将外部内容标记为数据。
- 工具权限由代码决定。
- 高风险动作需要显式确认。
- 不允许模型自行修改系统指令。
- 对输出做越权检测。

### 9.2 路径穿越

读取文件时不能只拼接字符串。应：

1. 将用户路径解析为规范绝对路径。
2. 检查它是否位于允许根目录内。
3. 拒绝 `..`、符号链接逃逸和设备文件。
4. 限制最大文件大小和读取时间。

### 9.3 任意命令执行

如果确实需要命令执行：

- 使用白名单命令和参数。
- 固定工作目录。
- 使用独立低权限用户或容器。
- 设置 CPU、内存、时间和输出限制。
- 默认禁用网络。
- 将命令和输出写入审计日志。

## 10. 评测 Agent

至少覆盖以下任务：

| 类别   | 示例                |
| ---- | ----------------- |
| 正常路径 | 使用正确工具完成任务        |
| 参数错误 | 模型传入缺失或非法参数       |
| 工具失败 | API 超时、文件不存在、权限拒绝 |
| 越权尝试 | 读取不允许目录或调用未授权工具   |
| 长任务  | 多步任务超过上下文或时间预算    |
| 重复执行 | 网络超时后再次提交写操作      |
| 恶意内容 | 文档中包含提示词注入        |

记录：

- 任务成功率。
- 工具选择正确率。
- 参数校验失败率。
- 平均和 P95 延迟。
- 平均工具调用数。
- 重试、超时和人工接管率。
- 越权调用拦截率。

## 11. 本地模型实践

使用 Ollama 时，Agent 通常通过 `/api/chat` 或兼容客户端访问模型。建议：

- 把 Ollama 当作不可信但可配置的推理依赖。
- 设置客户端连接和读取超时。
- 限制上下文长度和输出长度。
- 保存模型标签和 Modelfile 版本。
- 不把完整敏感数据写入调试日志。
- 把工具执行放在 Harness 中，而不是让模型直接控制进程。
