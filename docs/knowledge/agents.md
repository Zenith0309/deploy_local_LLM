# Agent 基础与实践

## 1. Agent 是什么

大语言模型本身通常只负责根据上下文生成下一段文本。Agent 则是在模型之上增加了目标、工具、状态和执行循环，让模型可以为了完成任务而采取多步行动。

一个实用的 Agent 通常包含：

| 组件 | 职责 |
| --- | --- |
| 模型 | 理解上下文、选择下一步行动、生成结果 |
| 指令 | 定义目标、边界、输出格式和行为规则 |
| 工具 | 读取文件、调用 API、执行受控命令或查询数据库 |
| 状态 | 保存当前任务、历史消息、中间结果和错误 |
| 执行器 | 调用模型、解析动作、执行工具并继续循环 |
| 验证器 | 检查结果是否满足格式、权限和业务要求 |

可以用下面的关系理解它们：

```text
用户目标 → Agent 指令 → 模型决策 → 工具执行 → 观察结果
                  ↑                         ↓
                  └──── 状态与验证 ←────────┘
```

## 2. Agent 与普通聊天的区别

普通聊天通常是：

```text
输入 → 模型 → 输出
```

Agent 更接近：

```text
目标 → 判断 → 调用工具 → 读取结果 → 再判断 → 验证 → 输出
```

因此 Agent 的难点不只是“让模型更聪明”，还包括工具设计、权限控制、状态一致性、超时和失败恢复。

## 3. 工具设计原则

一个好的工具应该：

- **单一职责**：完成一个清晰动作，而不是把整个系统塞进一个工具。
- **输入明确**：使用结构化参数、类型和范围校验。
- **输出稳定**：返回机器可读的结果，并包含必要的错误信息。
- **可重复或可追踪**：写操作需要幂等键、审计记录或预览模式。
- **权限最小化**：只开放完成任务所需的资源和操作。

不建议直接给 Agent 一个无限制的 Shell 工具。更安全的做法是提供白名单命令、固定工作目录、超时、输出大小限制和人工确认点。

## 4. 最小执行循环

一个最小 Agent 循环可以抽象为：

```text
while 未完成:
    读取目标、历史和工具结果
    请求模型选择下一步
    如果模型返回最终答案:
        验证答案并结束
    如果模型返回工具调用:
        校验参数和权限
        执行工具
        保存结果
    如果超过步数、时间或预算:
        停止并报告原因
```

循环必须有明确的停止条件。至少应设置最大步数、总超时、单次工具超时、输出长度和成本预算，避免模型在错误状态下无限调用工具。

## 5. 记忆与上下文

- **短期记忆**：当前对话和本次任务的工具结果。
- **长期记忆**：经过筛选后保存的用户偏好、事实或历史任务。
- **外部知识**：通过 RAG 从文档或数据库检索，不应把所有资料永久塞进提示词。

记忆不是越多越好。保存前要考虑敏感信息、过期信息、删除机制和来源可信度。对本地部署应用，建议默认数据留在本机，并为导出、清理和重置提供明确入口。

## 6. Agent 的安全边界

至少需要考虑：

1. 工具权限和资源范围。
2. 用户输入、网页内容和文件内容中的提示词注入。
3. 写文件、发消息、执行命令等高风险动作的确认。
4. 敏感数据是否会进入模型上下文或日志。
5. 工具调用和最终结果是否可审计。

Agent 的输出不能替代权限检查。即使模型声称“用户已经授权”，系统也应在工具层重新验证身份、资源和操作权限。

## 7. 本地模型上的实践建议

- 从一个只读工具开始，例如列出目录或查询本地文档。
- 先使用结构化输出，再增加多步工具调用。
- 给每个工具写正常、错误和边界输入测试。
- 记录模型版本、系统提示词、工具版本和关键参数。
- 用固定任务集评测成功率、工具调用次数、延迟和失败原因。
