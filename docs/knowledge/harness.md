# Harness 完整教程：让 Agent 可控、可观测、可恢复

## 1. Harness 的定义

Harness 可以理解为 Agent 的运行时控制层。它包裹模型、工具和任务状态，负责把一次自然语言请求变成有边界的、可审计的执行过程。

```text
模型：建议下一步做什么
Agent：围绕目标进行决策
工具：执行具体动作
Harness：决定能不能做、怎么做、做到什么时候、失败后怎么办
```

Harness 不是某个固定品牌或 SDK。一个 Python 服务、Node.js 任务执行器、CLI 框架或工作流编排器，只要承担这些控制职责，都可以称为 Harness。

## 2. 为什么不能只靠 Agent 提示词

提示词适合解释规则，但不能可靠执行规则：

- “最多调用五次工具”需要计数器。
- “只能访问某个目录”需要路径校验和沙箱。
- “发送前必须确认”需要状态机等待外部确认。
- “不能联网”需要网络策略。
- “输出必须是 JSON”需要解析和 Schema 验证。
- “失败后不能重复扣款”需要幂等键和业务约束。

因此，Harness 的核心思想是：**模型可以提出动作，但不能绕过运行时的验证和授权。**

## 3. Harness 的职责地图

| 层    | 典型职责                   |
| ---- | ---------------------- |
| 接入层  | 鉴权、请求限流、请求 ID、用户和租户识别  |
| 任务层  | 创建、排队、取消、暂停、恢复和清理任务    |
| 上下文层 | 组装消息、历史、工具定义和检索内容      |
| 模型层  | 调用模型、超时、流式输出、响应解析      |
| 工具层  | 注册工具、Schema 校验、路由和执行   |
| 策略层  | 权限、审批、网络、文件、预算和风险等级    |
| 状态层  | 状态机、检查点、幂等和一致性         |
| 验证层  | 输出 Schema、业务条件、引用和完成判定 |
| 观测层  | 日志、指标、追踪、审计和脱敏         |
| 恢复层  | 重试、回滚、人工接管、死信和故障诊断     |

## 4. 任务生命周期

推荐使用显式状态，而不是使用多个布尔字段猜测任务当前阶段：

```text
pending → running → waiting_approval → running
                 ├→ succeeded
                 ├→ failed
                 ├→ cancelled
                 └→ timed_out
```

状态转换应有约束：

- `pending` 才能开始运行。
- `running` 才能发起模型或工具调用。
- `waiting_approval` 只能等待批准、拒绝或过期。
- 终态不能再次执行，除非创建新的重试任务。
- 取消请求应能打断正在等待的模型和工具调用。

建议状态记录至少包含：

```text
task_id
parent_task_id
status
user_id / tenant_id
created_at / started_at / finished_at
step_count
model_name
prompt_version
tool_policy_version
last_event_id
last_error
deadline
budget_usage
checkpoint_ref
```

## 5. 一次完整执行流程

```text
1. 接收请求并生成 task_id
2. 鉴权、限流、检查输入大小
3. 创建任务状态和截止时间
4. 根据用户权限加载可用工具
5. 组装最小必要上下文
6. 调用模型
7. 解析为 final、tool_call 或 invalid
8. 对 tool_call 做名称、Schema、权限和风险检查
9. 需要审批时转为 waiting_approval
10. 执行工具并限制时间、输出和资源
11. 持久化工具结果和检查点
12. 回到模型或进入验证阶段
13. 验证最终输出和业务完成条件
14. 写入终态、指标和审计记录
```

其中第 8 步是安全关键点。模型输出不能直接传给 Shell、数据库或外部 API。

## 6. 上下文管理

Harness 负责决定哪些信息进入模型：

```text
系统规则
+ 用户目标
+ 当前任务状态
+ 必要的对话摘要
+ 当前允许的工具定义
+ 最近工具结果
+ 可信来源的检索片段
```

### 6.1 上下文预算

需要同时限制：

- 字符或 token 总量。
- 历史消息数量。
- 单个工具结果大小。
- 检索片段数量。
- 单次模型输出长度。

超过预算时，应按优先级压缩：先删除重复工具结果，再摘要旧对话，最后保留当前目标、约束和最近错误。不能静默截断关键安全规则。

### 6.2 版本化

任务应记录模型名称、系统提示词版本、工具 Schema 版本、策略版本和检索配置。否则发生错误时无法复现当时的执行环境。

## 7. 工具策略和权限

### 7.1 工具风险分级

可以把工具分成：

| 风险  | 示例            | 默认策略      |
| --- | ------------- | --------- |
| 低   | 计算、读取固定文档     | 自动执行      |
| 中   | 查询业务数据、生成草稿   | 权限检查和审计   |
| 高   | 写文件、修改数据、发送消息 | 显式审批或沙箱   |
| 极高  | 任意命令、付款、删除数据  | 默认禁用或人工操作 |

### 7.2 最小权限

权限应绑定用户、任务和工具，而不是只绑定模型：

```text
用户权限 ∩ 任务范围 ∩ 工具范围 ∩ 资源策略
```

例如，用户有权访问项目 A，不代表模型可以读取整个磁盘；任务允许读取文档，也不代表允许发送邮件。

### 7.3 审批

审批记录至少包含：

```text
approval_id
task_id
requested_action
risk_summary
requester
approver
decision
expires_at
```

审批必须有过期时间和明确的动作摘要，不能让用户批准一段无法理解的原始命令。

## 8. 超时、预算和取消

应同时设置：

- 连接超时。
- 读取超时。
- 单次工具超时。
- 单步模型超时。
- 总任务截止时间。
- 最大步骤数。
- 最大重试次数。
- 最大输出大小。
- 最大模型调用或资源预算。

取消不能只修改数据库字段。Harness 还需要向正在运行的模型请求、HTTP 请求、子进程或容器传递取消信号，并最终确认资源已经释放。

## 9. 错误分类和重试

### 不应重试

- 参数 Schema 错误。
- 权限拒绝。
- 路径不在允许范围。
- 用户明确取消。
- 业务规则冲突。

### 可以有限重试

- 临时网络断开。
- 上游服务限时不可用。
- 模型响应格式偶发错误。
- 并发冲突且支持重新读取。

指数退避示例：

```text
等待 1 秒 → 2 秒 → 4 秒 → 8 秒
```

必须设置上限和随机抖动，避免大量任务同时重试。

## 10. 幂等、检查点和恢复

### 10.1 幂等

网络超时并不代表写操作没有成功。重试前需要使用幂等键：

```text
idempotency_key = hash(task_id + logical_step + action_parameters)
```

服务端根据幂等键返回已有结果，而不是重复执行。

### 10.2 检查点

在高成本步骤前后保存：

- 当前状态。
- 已完成步骤。
- 工具调用和结果引用。
- 上下文摘要。
- 预算使用。
- 下一步计划。

检查点不应包含未经脱敏的密钥和不必要的敏感原文。

### 10.3 恢复策略

恢复时先判断：

1. 任务是否已经进入终态。
2. 最后一个工具调用是否可能已产生副作用。
3. 是否存在可验证的幂等结果。
4. 模型版本和策略版本是否仍兼容。
5. 是否需要人工接管。

不要简单地从最后一条消息重新执行所有动作。

## 11. 输出验证

验证分三层：

### 结构验证

检查 JSON、字段、类型、枚举、长度和必填项。

### 业务验证

检查资源是否存在、数值是否在范围内、状态是否允许转换。

### 事实验证

检查关键结论是否有工具结果、数据库记录或文档引用支持。

模型说“已经发送”不等于发送成功。只有工具返回成功并且业务系统确认，Harness 才能把任务标记为成功。

## 12. 观测、日志和审计

### 日志

建议记录：

- `request_id`、`task_id`、`user_id`。
- 模型和提示词版本。
- 工具名称、参数摘要和结果状态。
- 开始时间、结束时间和耗时。
- 重试、超时、审批和取消事件。

默认不要记录完整敏感提示词、API Key、个人身份信息和全部文档正文。

### 指标

至少跟踪：

- 任务成功率和失败率。
- P50/P95/P99 延迟。
- 模型加载时间。
- 工具调用次数和错误率。
- 平均重试次数。
- 超时和取消比例。
- 人工审批比例。
- 越权调用拦截次数。
- 上下文长度和内存使用。

### 追踪

一次任务应能串起：

```text
请求 → 模型调用 → 工具调用 → 外部服务 → 验证 → 最终状态
```

这样才能判断问题来自模型、工具、网络还是状态管理。

## 13. 与本地 Ollama 的集成

推荐架构：

```text
客户端
  ↓
应用 API / Harness
  ├─ 任务状态存储
  ├─ 工具注册和权限策略
  ├─ 超时、预算和审计
  └─ Ollama 客户端
        ↓
    Ollama API
        ↓
      本地模型
```

不要让浏览器直接获得高权限工具。浏览器只调用应用 API，由 Harness 决定是否向 Ollama 发起请求和是否执行工具。

## 14. 从最小 Harness 开始

推荐迭代顺序：

1. 单任务、单 Agent、无副作用的只读工具。
2. 增加结构化输出和 Schema 验证。
3. 增加任务状态、超时和最大步骤数。
4. 增加日志、指标和错误分类。
5. 增加检查点、恢复和幂等。
6. 增加审批和高风险写操作。
7. 增加并发、队列、租户隔离和回归评测。

不要一开始就实现多 Agent。多 Agent 会增加消息路由、状态一致性、权限传播、调试和成本控制难度。

## 15. Harness 测试清单

### 正常流程

- 模型返回合法工具调用。
- 工具返回成功。
- 最终答案通过 Schema 和业务验证。

### 异常流程

- 模型返回非法 JSON。
- 工具参数缺失或类型错误。
- 工具超时。
- 模型服务不可用。
- 任务超过预算。
- 用户在工具执行期间取消。
- 进程重启后从检查点恢复。
- 写操作在网络超时后重试。
- 模型尝试调用未授权工具。

每个测试都应检查最终状态、资源是否释放、审计记录是否完整，以及是否发生了重复副作用。
