# 1. 硬件评估、模型大小与量化选择

## 目标

完成本篇后，你应该能够：

- 区分磁盘、内存、显存和上下文缓存的占用。
- 根据设备资源选择首个模型。
- 理解 FP16、INT8、INT4、GGUF、GPTQ 和 AWQ 的基本关系。
- 在下载前估算风险，避免把系统盘或显存打满。

## 1. 四类资源

| 资源 | 影响 | 常见症状 |
| --- | --- | --- |
| 磁盘 | 模型文件、缓存、容器卷 | 下载失败、系统盘不足 |
| 系统内存 | CPU 推理、GPU offload、上下文 | 系统卡顿、进程被杀 |
| 显存 | GPU 权重、KV Cache、运行时缓冲 | CUDA out of memory |
| 计算能力 | token/s、并发和延迟 | 首 token 慢、吞吐不足 |

模型文件大小不等于运行时内存。运行时还需要加载权重、KV Cache、临时张量和框架开销。

## 2. 选择规模

| 设备 | 第一个模型 | 适合任务 |
| --- | --- | --- |
| 8 GB 内存、无独显 | 1B-3B | 摘要、简单问答 |
| 16 GB 内存 | 3B-7B 量化 | 中文问答、代码辅助 |
| 6-8 GB 显存 | 7B/8B 量化 | 交互式对话 |
| 12-16 GB 显存 | 7B/14B 量化 | 更复杂的文本和代码任务 |
| 24 GB 以上显存 | 14B 及以上 | 更高质量或更长上下文 |

这是起点而不是保证。上下文长度、并发数和模型架构都会改变实际需求。

## 3. 量化如何影响部署

量化用较低精度表示权重，以减少存储和计算开销。通常可以这样理解：

```text
FP16/BF16：质量和资源占用较高
INT8：质量损失较小，资源下降
INT4：资源友好，适合消费级设备
```

常见格式：

- **GGUF**：常见于 llama.cpp、Ollama 等本地 CPU/GPU 混合推理。
- **GPTQ/AWQ**：常见于 GPU 推理服务和特定量化工具链。
- **Q4/Q5/Q8**：表示量化等级的常见命名，不能只看数字判断质量。

第一次部署优先选择模型库中已经验证过的量化版本，不要先从原始权重自行量化。

## 4. 下载前检查表

```text
[ ] 操作系统和 GPU 后端受支持
[ ] 模型标签真实存在
[ ] 磁盘有模型大小两倍左右的余量
[ ] 内存/显存满足模型和上下文的需要
[ ] 模型许可证允许你的使用场景
[ ] 已准备一个小模型用于验证工具链
```

## 5. 建立自己的基线

固定三个问题，分别记录模型加载时间、首 token 延迟、生成速度和回答质量。以后更换量化版本或上下文长度时，只改变一个变量。
